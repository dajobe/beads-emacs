# Contributing

Contributions to `bv-emacs` are welcome. Keep changes focused, preserve the
separation between `br` mutations and `bv` analysis, and include regression
coverage for behavior changes.

## Development setup

The development requirements are Emacs 29.1 or newer, `make`, and local `br` and
`bv` executables for integration testing. The unit tests replace the command
runner where possible, so most tests do not mutate a real Beads workspace.

Clone the repository and run:

```console
make check
```

The Makefile uses `emacs` from `PATH`. On macOS it falls back to
`/Applications/Emacs.app/Contents/MacOS/Emacs`; set `EMACS` explicitly for any
other installation:

```console
make check EMACS=/path/to/emacs
```

## Quality targets

| Target                          | Purpose                                                    |
|:--------------------------------|:-----------------------------------------------------------|
| `make build`                    | Byte-compile package files with warnings treated as errors |
| `make test`                     | Build the package and run the full ERT suite               |
| `make checkdoc`                 | Check package comments and docstrings                      |
| `make lint`                     | Run package-lint when it is installed                      |
| `make install-dev-dependencies` | Install package-lint from MELPA                            |
| `make check`                    | Run all supported quality checks                           |
| `make install`                  | Install source and byte-compiled files locally             |
| `make clean`                    | Remove generated byte-compiled files                       |
| `make install-pre-commit-hook`  | Install a Git hook that runs `make check`                  |

`package-lint` is optional so contributors can run the core suite with a stock
Emacs installation. Run `make install-dev-dependencies` or install it from your
preferred Emacs package archive to enable that additional target. CI installs it
before running the suite.

## Testing changes

Add ERT tests under `tests/`. Prefer testing command argument lists, JSON
normalization, rendering, and state transitions without installed `br` or `bv`
binaries. Use a temporary Beads workspace for behavior that needs discovery or
process integration; never depend on a developer's real issue database.

Before submitting a change, run:

```console
make check
git diff --check
```

CI runs the same suite on Emacs 29 and Emacs 30.

## Design constraints

- Prefix package symbols with `bv-`.
- Pass commands as argument lists to `make-process` or `process-file`; do not
  construct shell commands.
- Request and decode JSON for all machine-readable `br` and `bv` output.
- Use only `bv --robot-*` commands. Bare `bv` launches an interactive TUI.
- Send every normal mutation through `br`; do not edit `.beads` files or the
  database directly.
- Keep the core runner replaceable and keep rendering logic testable without
  external processes.
- Confirm destructive or state-ending actions and retain useful stderr when a
  subprocess fails.

See [Architecture](architecture.md) for the package boundaries and workspace
model.

## Issue workflow

This repository uses Beads for issue tracking. Start with `bv --robot-triage`,
verify the selected issue with `br show ID --json`, and use `br` to claim and
close work. Flush mutations to the tracked JSONL export with the `br sync
--flush-only` command.
